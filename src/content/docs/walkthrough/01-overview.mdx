## Purpose

This walkthrough documents how to deploy and operate the [tfstack/terraform-aws-ipam](https://github.com/tfstack/terraform-aws-ipam/tree/main/examples/multi-account/) example — a <Tooltip term="terraform" label="Terraform" /> demo for four-account <Tooltip term="ipam" label="IPAM" /> with ANZ regional pools, <Tooltip term="ram-share" label="RAM sharing" />, and pool-backed workload VPCs.

A dedicated <Tooltip term="network-account" label="network account" /> hosts org-wide IPAM in `ap-southeast-6`. Dev and sandbox workload accounts allocate `/20` VPC CIDRs from RAM-shared leaf pools in matching regions.

The pattern uses `ipv4_ipam_pool_id` via `modules/ipam-vpc/`. It does **not** use Transit Gateway, VPC peering, NAT gateway, or management-account IPAM hosting.

## Accounts, regions, and stacks

| Stack            | Account    | Profile           | Region           |
| ---------------- | ---------- | ----------------- | ---------------- |
| `org-bootstrap/` | Management | `ipam-org`        | Global           |
| `ipam/`          | Network    | `ipam-network`    | `ap-southeast-6` |
| `workload-a/`    | Dev        | `ipam-workload-a` | `ap-southeast-6` |
| `workload-b/`    | Sandbox    | `ipam-workload-b` | `ap-southeast-2` |

Leaf pools and expected VPC CIDRs:

| Pool path        | Locale           | Workload VPC    |
| ---------------- | ---------------- | --------------- |
| `org/nz/dev`     | `ap-southeast-6` | `10.64.0.0/20`  |
| `org/au/sandbox` | `ap-southeast-2` | `10.128.0.0/20` |

## Phased dependency model

| Step                          | Depends on       | Why                                                                  |
| ----------------------------- | ---------------- | -------------------------------------------------------------------- |
| `ipam/`                       | `org-bootstrap/` | Needs delegated admin and RAM org sharing                            |
| `workload-a/` / `workload-b/` | `ipam/`          | Needs `pool_id` from `nz_dev_pool_id` / `au_sandbox_pool_id` outputs |

Workloads may run in parallel after `ipam/` completes.

## Success criteria

Deployment succeeds when all of the following are true:

- Leaf pools `org/nz/dev` and `org/au/sandbox` exist with expected CIDRs and locales
- RAM shares `org-nz-dev` and `org-au-sandbox` are **Active**
- Workload VPCs are **Managed** via `ipv4_ipam_pool_id`
- Planning → Pools → **Allocations** shows `/20` blocks owned by workload accounts
- Monitoring → **Resources** lists the pool-backed VPCs as **Managed** (filter by account and CIDR)

## Intentionally excluded

The upstream example deliberately omits:

- Transit Gateway, VPC peering, VPN, or Direct Connect
- NAT gateway (disabled for cost)
- Public IPAM scope usage
